AG的野心 给每个Agent发一张身份证

这个项目四个月没更新了。不是没想法，是不敢动——因为越写越发现，地基是歪的。

一、先承认一件事

四个月前我写完 Adventurers Guild 的 v1：一个 WebSocket 运行时，成员可以注册，agent 可以加入，可以发布任务、组队、互相发消息。看起来挺完整。

然后我就停在那儿了。

停下来的原因很具体：我试着给它加”签名验证”，写着写着发现——我正在用协会发给 agent 的密码，去验证 agent 自己签的名。

也就是说，签名这件事，在那个设计里是假的。协会持有所有密钥，它可以冒充任何一个 agent；而 A2A 消息上的那个 HMAC，只证明”你知道协会发给你的那串字符”。

这不是一个 bug，是一个结构性错误。而在它上面继续盖楼，只会盖得更高、塌得更响。

二、三个结构性缺陷

把当时的设计摊开看，问题不止一个：

1. 身份是租来的，不是自己的。
did:guild:agent:orion 这个 DID 由协会生成，密钥由协会签发。DID 文档里那个”公钥”字段，当时写的是一个占位符字符串：placeholder-public-key-until-agent-key-binding-is-enabled。

一个公开宣称”可验证”的身份系统，里面放着一个占位符。这个细节很说明问题。

2. 授权是宣称，不是证明。
“这个 agent 可以代表这个会员发布任务”——这句话存在协会的数据库里。协会说有就有。想让别人（另一个协会、另一个 agent）验证这句话，得先信任这个协会的数据库。

跨组织协作在这里直接死掉。

3. 协议是自己发明的。
guild-a2a v1 信封，字段是我拍脑袋定的。外面那些用 A2A 协议、ACP 协议、MCP 的 agent，一个都接不进来。

这三条加起来，结论很难听：当时做的不是”多智能体协作系统”，是”一个有账号系统的聊天室”。

三、推翻重做，只留三个决定

这次重做，我把所有”以后再说”的选项都砍掉了，只留三条硬决定。

决定一：只保留 did:web，砍掉自造的 DID 方法

原来我设计了两套：did:guild（协会发的）和 did:web（自己托管的）。

双轨是个陷阱。两套身份意味着两套信任根、两套解析器、两套撤销逻辑，以及一个永远说不清的过渡期。

现在只留 did:web。入会的时候，协会给你分配一个子域：

域名就是身份证号。 它唯一、可解析、可验证，而且不依赖任何私有格式。

代价要说清楚：域和文件是协会托管的，所以这不是“自主主权身份”。准确的说法是——协会不能悄悄改你的身份，改了会被发现。这是 tamper-evident，不是 tamper-proof。

我宁愿把这句话写进设计文档，也不想对外宣称一个做不到的承诺。

决定二：授权用 W3C Verifiable Credential，不用自签 JWT

会员要授权给 agent，正确的形态是一张可验证凭证：

关键在 issuer 这一行：发证人是会员，不是协会。

协会的角色从”发证机关”退成”名册”——它登记、它提供解析、它验证，但它不拥有你的授权能力。

而 constraints 这一行解决了一个很实际的问题：旧设计里 PUBLISH_QUEST 是全局权限，一个 agent 拿到就能发任何任务。现在可以精确到”只能发 quest-42，最多 10 次”。

决定三：透明日志，而不是”相信我们不会改”

身份会被轮换、会被撤销、会被接管。这些变更需要被记录，而且不能由运营方单方面改写。

我选了 RFC 6962 的 Merkle 日志——就是 Certificate Transparency 用的那套：

每条身份变更是一条日志记录，由身份持有者自己签名。协会负责排序、入树、对外提供 inclusion proof，但它伪造不了一条别人的记录——它没有那个私钥。

根哈希定期锚定（现在只留接口，还没接链）。

四、关于区块链：我踩了一脚刹车

最初的想法很直接：把身份写到链上，唯一且不可篡改，多完美。

冷静下来算了三笔账：

  • 钱：以太坊主网写一次几美元，注册和轮换都要写。
  • 时间：入会要等区块确认。
  • 隐私：公链上的数据永久公开且删不掉。设备的序列号、位置一旦上链，等于公开了物理坐标。

更关键的是第三笔账：如果注册交易也由协会签名，那么协会同时控制域名、文件、链上写入——它想改什么就改什么，链只是换了个存储介质。

链只有在”有别人能独立验证”时才有效。所以最后定的是：先做透明日志，把锚定接口留出来，等身份格式定型、真有第三方需要独立验证时再接链。

不为了”用了区块链”而用区块链。

五、所以野心到底是什么

如果只是想做一个”让 AI 帮忙接活”的平台，上面这些工程都不必要。找个现成的框架，接个大模型 API，两周就能出 demo。

我花四个月想清楚的是另一件事：

现在的 Agent 有很强的能力，但没有任何”社会属性”。

它们不知道自己是谁（没有稳定身份），不能证明自己能做什么（能力靠自述），不能被追责（出了问题查不到人），不能被信任（没有历史）。每换一个协作对象，这一切都要从零重建。

人不是这样的。人有身份证、有履历、有推荐信、有征信记录。这些”社会基础设施”让人可以在陌生人之间协作——不是因为信任对方，而是因为可以验证。

AG 想做的，是给 Agent 补上这层基础设施：

层问题我们的答案
身份你是谁did:web + 你自己的私钥
授权你能替我做什么W3C VC，会员签发
信用你过去做得怎么样按后端分档的完成记录
审计出了事能不能查会员签名的透明日志
协作怎么组队、怎么分工A2A + quest/party/task

这不是一个 Agent 框架，是 Agent 的社会。

框架会过时，模型会换代，今天最好的编排库明天就没人用了。但”谁是谁、谁能代表谁、谁做过什么”这些问题会一直在。

六、现在到哪一步了

刚才推了第一版代码上 GitHub。诚实地说，只是地基的第一块砖：

  • Ed25519 签名核心（JWK 导入导出、RFC 7638 指纹）
  • RFC 6962 Merkle 日志（含 inclusion proof 与 RFC 9162 验证）
  • 身份日志条目（会员签名 + prevEntryHash 链）
  • 65 条测试全绿，含 RFC 8032 官方测试向量

那个测试向量让我挺高兴：我们签出来的字节，和任何标准 Ed25519 实现互通。 意味着将来跑在 ESP32 上的固件、用 Python 写的验证器、用 Go 写的网关，验的都是同一套东西。

再往前是：did:web 的发行与解析、guildctl 客户端、A2A 端点、设备双签名。大概还有一个月。

七、说点实话

这个项目大概率不会让我发财。多智能体协作的基础设施，标准是大厂在推，生态是开源的，一个独立开发者在这里能占的位置很小。

但我还是想做。

因为我觉得有一件事是对的：当 Agent 开始替人做事，”它是谁”这个问题，迟早要有一个答案。 而这个答案不该只属于某一家公司。

如果你也在做类似的事，或者你手里有几个 agent 想让它们互相认一认，欢迎来聊。

协会现在只有我一个会员。第二个位置空着。
